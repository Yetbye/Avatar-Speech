01 一句话读懂：一个「简洁但强大」的统一建模与优化框架

JavisDiT++（ICLR 2026）延续 JavisDiT 谱系，目标是把联合音视频生成（JAVG）的建模与优化统一起来。它自称「concise yet powerful」，核心设计是一个 模态专属混合专家（MS-MoE）：在保持跨模态交互效率的同时，让每个模态有自己的专家路径。它还系统研究了「如何把 Wan2.1-T2V 适配到联合音视频生成」的架构设计。

深度洞察

MS-MoE 是「统一」与「分工」的折中解

联合生成面临一个根本张力：完全共享（Apollo 单塔）表达力受限，完全分开（Ovi 双塔）同步靠融合。MS-MoE 给出第三条路——共享路由 + 模态专属专家：既让模态在关键计算上分工（各走各的专家），又让它们在路由层面交互。这与「共享语义、分工渲染」的模式（JAVIS）精神一致，只是把分工点放在了专家层。

02 MS-MoE：模态专属混合专家

图 1 · MS-MoE：共享路由 + 模态专属专家，介于单塔与双塔之间
模态专属专家
视频与音频各有专属专家，负责模态特化计算。避免「一个专家硬学两种信号」的表达力浪费。
共享 Router
路由层让模态信息交互，决定 token 走哪个专家。交互效率高（不需每层全注意力）。
跨模态效率
原文强调 MS-MoE 在保持跨模态交互有效性的同时提升效率。相比全注意力（Apollo）省算力，相比逐层融合（Ovi）更灵活。
统一建模
同一框架下做建模与优化的统一。「简洁但强大」的设计哲学。

「适配研究」是连接研究界与工程界的桥

很多论文只提「我们的架构更好」，却不回答「如果你想在现有 T2V 上做，该怎么改」。JavisDiT++ 的架构消融正是回答后者——它把「哪些设计真的有用」量化出来，让工程师不必从零试错。这类「适配指南」类贡献实用价值很高，但常被学术评价低估。

04 关键公式（示意性形式化）

Eq.1 · MS-MoE 的路由（示意）
$$ y = \sum_{m \in \{v,a,s\}} g_m(x)\cdot E_m(x), \qquad g = \text{Softmax}(\text{Router}(x)) $$
直觉：每个 token 经共享路由器 g 决定走视频专家 E_v、音频专家 E_a 或共享专家 E_s，输出加权和。
注意：此式为按 MoE 范式的示意性形式化；原文的路由设计（是否 top-k、专家数）需查原文。
Eq.2 · 三维度权衡（示意）
$$ \mathcal{L} = \lambda_q \mathcal{L}_{\text{quality}} + \lambda_c \mathcal{L}_{\text{consistency}} + \lambda_s \mathcal{L}_{\text{sync}} $$
直觉：三个度量维度各有权重，架构选择影响三者的帕累托前沿。λ 反映应用取向（如直播更看重同步）。

06 批判评估

批判评估

1. 「concise」缺少效率数字支撑

自称简洁高效，但抽取文本未见明确的参数量/延迟/吞吐对比。若无效率数字，「简洁」只是定性说法。相对 LTX-2（18× 加速）、VDN（3.38×），本文的效率主张需更硬的数据。

批判评估

2. 只报 11 个指标中的 7 个

原文称「for efficiency, we report 7 out of the 11 full metrics」。选择性报告可能隐藏不利维度。理想做法是全部报告，或说明被省略的 4 个为何不重要。

批判评估

3. 与前身 JavisDiT 的提升幅度需明确

同系列工作，JavisDiT++ 相对 JavisDiT 的增量贡献应清晰量化。若提升主要来自更细的调参而非 MS-MoE，则「统一框架」的贡献被高估。

批判评估

4. MoE 的训练稳定性与路由坍塌未讨论

MoE 常见问题是路由坍塌（所有 token 挤到一个专家）。模态专属专家有一定缓解（天然分工），但共享专家仍可能被冷落。需报告各专家的负载分布。

07 自主科研问题

自主科研问题 · Q1

专家数与模态数该如何配比？

未知与意义：MS-MoE 用视频/音频/共享专家。若细分（如音频再分语音/音效），收益如何？

理论分析：专家数应与「模态内部的子分布数」匹配。音频含语音、音效、音乐三种，用单一音频专家可能欠拟合。可用聚类估计最优专家数。

连接：Soundwich 的多声源分轨是「按声源分专家」的极端化；两者构成粒度光谱。

探究方向：扫描音频专家数（1/2/4），测语音、音效、音乐各维度的生成质量。

自主科研问题 · Q2

MoE 的路由能否承担「同步对齐」的功能？

未知与意义：路由决定 token 走哪个专家，但未显式考虑同步。若把「同步对齐」编码进路由，是否更好？

理论分析：可把路由扩展为「带时间感知」的路由：同时匹配模态与时间片，使同一事件的音视频 token 走同一专家。

连接：JavisDiT 的 HiST-Sypo 显式估计同步先验；若把先验接入路由，是两条路线的融合。

探究方向：对比普通路由与时间感知路由，测同步指标的提升。

自主科研问题 · Q3

「适配研究」的结论能否跨骨干泛化？

未知与意义：架构消融在 Wan2.1-T2V 上做。这些结论对 LTX-2、Wan2.2 等其他骨干是否成立？

理论分析：若架构设计的收益来自「通用的模态分工原理」，则应跨骨干泛化；若来自「Wan2.1 的特定结构」，则不普适。可做跨骨干验证。

连接：OmniForcing 用 LTX-2 作教师、MOVA 用 Wan2.2——不同骨干的选择影响结论迁移。

探究方向：在 2-3 个骨干上重跑关键消融，测结论一致性。

# MS-MoE：共享路由 + 模态专属专家（示意，非官方实现）
class MSMoE(nn.Module):
    def __init__(self, dim):
        super().__init__()
        self.router   = nn.Linear(dim, 3)   # 视频/音频/共享
        self.exp_v    = Expert(dim)          # 视频专家
        self.exp_a    = Expert(dim)          # 音频专家
        self.exp_shared = Expert(dim)        # 共享专家

    def forward(self, x, modality):
        g = F.softmax(self.router(x), dim=-1)   # 共享路由
        out = g[...,0:1]*self.exp_v(x) + g[...,1:2]*self.exp_a(x) + g[...,2:3]*self.exp_shared(x)
        return out

深度洞察

「简洁」的真正含义：用更少的机制覆盖同样的能力

好的「简洁」不是功能少，而是机制少、覆盖广。MS-MoE 用一个路由机制同时处理「模态分工」与「跨模态交互」，比单塔的全注意力、双塔的逐层融合都更省机制。但「简洁」必须有证据——这正是批判 #1 指出的缺口：没有效率数字，简洁只是口号。这也提醒评价工作时：看它省了什么、付了什么，而不是看它自夸什么。
